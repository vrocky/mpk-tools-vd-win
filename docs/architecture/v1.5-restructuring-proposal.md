# Main v1.5 Improvement

The best change is this:

```txt
src/
├── desktop/      → actual WPF GUI apps
├── launchers/    → PowerShell virtual desktop launchers
├── shared/       → reusable C# libraries
├── features/     → app-specific helper modules/search tools
└── tools/        → updater and internal utilities
```

This is much cleaner than the current structure where `apps/` contains WPF apps, shared libraries, feature modules, and POC code together. The current file specifically says the shared library is stored inside `apps/`, which makes it hard to discover. 

# Better Naming

Instead of:

```txt
mpk-tools-win-virtual-desktop-chrome-launch
mpk-tools-vscode-profile-picker
mpk-tools-mpk-profile-common-libs
```

Use short folder names inside the main repo:

```txt
src/launchers/chrome/
src/desktop/MPK.VsCode.ProfilePicker/
src/shared/MPK.Profile.Core/
```

The GitHub repo/submodule name can remain long if needed, but the **local folder name should be clean**.

Example:

```txt
[submodule "src/launchers/chrome"]
    path = src/launchers/chrome
    url = https://github.com/vrocky/mpk-tools-win-virtual-desktop-chrome-launch.git
```

So you do not need to rename all GitHub repos immediately.

# Better Way to Do the Same Work

## Current Way

Each launcher has its own hardcoded logic:

```txt
Chrome launcher knows Chrome path
VS Code launcher knows VS Code path
Claude launcher knows Claude path
Each launcher hardcodes profile folder
Each launcher repeats virtual desktop detection logic
```

This creates duplicate logic and makes every new app harder to maintain.

## v1.5 Way

Create one common launcher engine:

```txt
src/launchers/_shared/
├── VirtualDesktop.psm1
├── ProfilePath.psm1
├── AppLauncher.psm1
└── Shortcut.psm1
```

Then each app launcher becomes mostly configuration:

```txt
src/launchers/chrome/
├── launcher.ps1
└── launcher.config.json
```

Example:

```json
{
  "appId": "chrome",
  "displayName": "Google Chrome",
  "executablePath": "C:\\Program Files\\Google\\Chrome\\Application\\chrome.exe",
  "profileRoot": "C:\\MPKProfiles\\Chrome",
  "arguments": [
    "--user-data-dir={profilePath}"
  ],
  "profileStrategy": "virtual-desktop"
}
```

Then `launcher.ps1` becomes very small:

```powershell
Import-Module "$PSScriptRoot\..\_shared\AppLauncher.psm1"

Start-MpkVirtualDesktopApp `
  -ConfigPath "$PSScriptRoot\launcher.config.json"
```

This is much better because the logic lives once, and each app only provides config.

# v1.5 Build Structure

Move from:

```txt
installer/Build-MpkToolsInstaller.ps1
```

to:

```txt
build/Build.ps1
```

And internally split it:

```txt
build/
├── Build.ps1
├── Publish-DesktopApps.ps1
├── Publish-Launchers.ps1
├── Stage-Installer.ps1
└── New-Release.ps1
```

The current build process publishes WPF apps, copies launchers, stages updater, runs Inno Setup, and creates the final installer. That flow is fine, but it should not all live as one tightly coupled installer script. 

Recommended command:

```powershell
.\build\Build.ps1 -Configuration Release -Version 1.5.0
```

Output:

```txt
dist/
├── staging/
│   └── MPKTools/
└── output/
    └── MPK-Tools-Setup-1.5.0.exe
```

# v1.5 Versioning

Add a simple root-level file:

```txt
VERSION
```

Content:

```txt
1.5.0
```

Then every build reads from this file unless overridden:

```powershell
.\build\Build.ps1
```

or:

```powershell
.\build\Build.ps1 -Version 1.5.1
```

This avoids manually passing `InstallerVersion 1.0.0` every time. The current process has manual versioning and manual release upload, which is one of the documented problems.

Profile data should not live inside Program Files.

Use:

```txt
C:\MPKProfiles\
├── Chrome\
├── Edge\
├── VSCode\
├── Claude\
└── StickyNotes\
```

Or better future option:

```txt
%LOCALAPPDATA%\MPKTools\Profiles\
```

But for your current use case, `C:\MPKProfiles\` is cleaner than many separate folders like:

```txt
C:\ChromeProfiles\
C:\VSCodeProfiles\
C:\ClaudeProfiles\
```

The uploaded context notes that profile folders are currently hardcoded separately, such as `C:\ChromeProfiles\`, which makes customization difficult.
