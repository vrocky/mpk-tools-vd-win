## Executive Summary

**MPK Tools** is a Windows 11 productivity suite that enables isolated application profiles per virtual desktop. The project consists of:

1. **WPF Desktop Applications** (C#/.NET 8) — GUI-based profile managers for VS Code, Sticky Notes
2. **PowerShell Launch Scripts** (14 submodules) — Virtual desktop-aware launchers for browsers, text editors, and other apps
3. **Shared Library** — Common functionality (registry, profile detection, COM interop)
4. **Unified Installer** — Inno Setup-based `.exe` that bundles all components into `C:\Program Files\MPK Tools\`

**Goal:** Solve fragmented user data across Windows virtual desktops by allowing each application instance to have its own isolated profile, settings, and extensions.

## Component Breakdown

### 1. WPF Desktop Applications (.NET 8, C#)

These are GUI applications that let users manage and launch isolated profiles for specific tools.

| App | Purpose | Location | Profile Storage |
|-----|---------|----------|-----------------|
| **VS Code Profile Picker** | GUI to select and launch VS Code with isolated extensions/settings | `apps/mpk-tools-vscode-profile-picker` | `C:\VSCodeProfiles\` |
| **Sticky Notes Profile Picker** | GUI to select and launch Sticky Notes with isolated data per desktop | `apps/mpk-tools-sticky-notes-profile-picker` | `C:\StickyNotesProfiles\` |
| (Future) AntiGravity/Chrome Pickers | Similar pattern for other apps | `apps/mpk-tools-*-profile-picker` | App-specific |

**Key Features:**
- WPF dark theme UI (`#1e1e1e` background)
- Real-time searchable profile grid
- Registry-backed persistence (no config files)
- Auto-generated profile avatars with initials + color
- Settings window to add/remove profile directories
- Shared core library for registry operations and profile scanning

**Build Output:**
- Self-contained `.exe` (no .NET runtime required)
- Signed installer integration

---

### 2. PowerShell Launch Scripts (14 repos, each ~10–50 KB)

These are thin PowerShell wrappers that detect the current Windows virtual desktop and launch an application with an isolated profile folder.

| App | Launch Script Repo | Profile Location |
|-----|-------------------|------------------|
| **AntiGravity** | `mpk-tools-win-virtual-desktop-antigravity-launch` | `C:\AntiGravityProfiles\virtual_desktop_[N]\` |
| **Chrome** | `mpk-tools-win-virtual-desktop-chrome-launch` | `C:\ChromeProfiles\virtual_desktop_[N]\` |
| **Claude** | `mpk-tools-win-virtual-desktop-claude-launch` | `C:\ClaudeProfiles\virtual_desktop_[N]\` |
| **Edge** | `mpk-tools-win-virtual-desktop-edge-launch` | `C:\EdgeProfiles\virtual_desktop_[N]\` |
| **Sticky Notes** | `mpk-tools-win-virtual-desktop-sticky-notes-launch` | `C:\StickyNotesProfiles\virtual_desktop_[N]\` |
| **VS Code** | `mpk-tools-win-virtual-desktop-vscode-launch` | `C:\VSCodeProfiles\virtual_desktop_[N]\` |

**What They Do:**
1. Detect current virtual desktop via Windows registry or COM API (`IVirtualDesktopManager`)
2. Compute profile folder name: `virtual_desktop_[N]`
3. Create isolated `--user-data-dir` if not already present
4. Launch application with flags like `--user-data-dir "C:\ChromeProfiles\virtual_desktop_1\"`
5. Optional: Create desktop `.lnk` shortcut

**Virtual Desktop Detection Mechanisms:**
- **Registry approach (primary):** Read `HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\VirtualDesktops`
  - `CurrentVirtualDesktop` (REG_BINARY GUID of active desktop)
  - `VirtualDesktopIDs` (concatenated GUIDs)
- **COM approach (per-window):** Use `IVirtualDesktopManager` (CLSID `AA509086-5CA9-4C25-8F95-589D3C07B48A`)
  - Methods: `IsWindowOnCurrentVirtualDesktop()`, `GetWindowDesktopId()`, `MoveWindowToDesktop()`
  - More reliable for window-specific queries; wrapped in C# shim for PowerShell

### 3. Shared Library

**`mpk-tools-mpk-profile-common-libs`** — Located in `apps/`

Contains reusable code for:
- **Registry Operations:** Read/write profile settings to `HKEY_CURRENT_USER\Software\VsCodeProfilePicker` (or app-specific keys)
- **Profile Scanning:** Enumerate profile folders and detect subdirectory structure
- **Virtual Desktop Detection:** Wrapper around registry and COM APIs
- **Recent Project Parsing:** Extract project/workspace metadata from VS Code settings

Used by:
- VS Code Profile Picker (main consumer)
- Potentially shared across future Sticky Notes and other WPF apps

**Current Location Issue:** Named `mpk-profile-common-libs` but stored in `apps/` alongside non-library submodules, making it hard to discover.

### 4. Proof-of-Concept (POC)

**`mpk-tools-win-virtual-desktop-poc`** — Located in `apps/`

A temporary testing ground for virtual desktop detection logic. Likely contains:
- Registry GUID parsing examples
- COM API calling patterns
- Window enumeration utilities

**Status:** Should be either promoted to shared library, archived, or removed.

### 5. Installer & Packaging

**Location:** `installer/`

**Files:**
- `Build-MpkToolsInstaller.ps1` — PowerShell script that:
  - Publishes all .NET 8 WPF apps as self-contained binaries
  - Copies PowerShell launch scripts from submodules
  - Stages updater executable
  - Runs Inno Setup compiler
  
- `MPKTools.iss` — Inno Setup configuration:
  - Installs to `C:\Program Files\MPK Tools\`
  - Uses stable AppId (allows in-place upgrades)
  - Creates Start Menu shortcuts for all apps/launchers
  - Optionally creates desktop shortcuts
  - Installs updater exe at `C:\Program Files\MPK Tools\Updater\MPKToolsUpdater.exe`

- `MPKToolsUpdater/` — Standalone .NET updater app:
  - Queries GitHub Releases for latest version
  - Downloads installer via `gh release download`
  - Runs silent install with `/VERYSILENT /SUPPRESSMSGBOXES`
  - No in-app update logic in individual apps (decoupled)

**Output:**
- `installer\dist\output\MPK-Tools-Setup-<version>.exe` — Final installer
- `installer\dist\staging\` — Intermediate staging directory (for debugging/manual builds)

**Update Strategy (Documented):**
- Suite-level updates via full installer replacement (not per-app self-updates)
- GitHub Releases as source (no external manifest server)
- Updater uses authenticated `gh` CLI
- Asset naming convention: `MPK-Tools-Setup-<version>.exe`

## What Needs Improvement (For Next Agent)

### Structural Issues

1. **Directory Organization**
   - `apps/` mixes WPF applications, PowerShell launchers, and shared libraries
   - Naming is inconsistent and verbose (e.g., `mpk-tools-win-virtual-desktop-chrome-launch`)
   - No clear visual separation of concerns

2. **Packaging & Build Process**
   - Single monorepo with 14 submodules — difficult to manage independently
   - Build script (`Build-MpkToolsInstaller.ps1`) is tightly coupled to directory structure
   - No clear version management across suite components

3. **Installer & Distribution**
   - Update strategy documented but not integrated into CI/CD
   - Manual versioning required (`InstallerVersion 1.0.0` parameter)
   - Unclear how to publish releases consistently

4. **Professionalism**
   - No top-level README
   - No contributing guidelines
   - Update strategy is buried in docs, not enforced by build system
   - No version tagging or semantic versioning policy

### Suggested Improvements (Not Prescriptive)

**Phase 1: Restructure**
- Create logical top-level folders:
  - `src/apps/` — WPF applications only
  - `src/launchers/` — PowerShell virtual desktop launchers
  - `src/shared/` — Shared libraries
  - `tools/` or `infra/` — Installer, updater, build scripts
- Rename submodules to shorter, semantic names if possible (or alias them)
- Move POC to separate branch or archive

**Phase 2: Improve Build & Packaging**
- Automate version bumping and semantic versioning
- Integrate update strategy into CI/CD pipeline
- Create unified build script that respects new structure
- Produce versioned release artifacts consistently

**Phase 3: Documentation**
- Add top-level README with architecture overview
- Document each component's purpose and how to extend
- Create contribution guidelines
- Document release process

## Build & Release Process (Current)

```
1. Developer commits code to feature branch
2. Manual trigger of Build-MpkToolsInstaller.ps1:
   PowerShell> .\Build-MpkToolsInstaller.ps1 -Configuration Release -Runtime win-x64 -InstallerVersion 1.0.0
   
3. Script performs:
   - Pull latest submodule changes
   - Publish all .NET 8 WPF apps (self-contained)
   - Copy PowerShell launch scripts
   - Build updater executable
   - Stage everything to installer\dist\staging\
   - Run Inno Setup compiler → installer\dist\output\MPK-Tools-Setup-1.0.0.exe
   
4. Manual upload to GitHub Releases as asset
5. Release notes manually authored
6. Users download installer and run
7. Post-install, users can run updater to check for new versions
```

**Problems:**
- Version bumping is manual
- No CI/CD automation
- Release consistency depends on manual steps
- Update strategy not enforced

## Known Constraints & Open Questions

1. **Submodule Decay Risk** — 14 independent repositories make it easy for versions to drift
2. **Virtual Desktop Detection Fragility** — Registry approach accumulates historical GUIDs; COM API is more reliable but adds complexity
3. **Profile Folder Hardcoding** — Each launcher hardcodes profile path (e.g., `C:\ChromeProfiles\`) — difficult to customize
4. **Missing CI/CD** — No automated tests, builds, or releases
5. **Installer Signing** — Update strategy mentions code signing but mechanism not yet in place
6. **User Expectations** — No UI feedback on update availability until updater is manually launched
